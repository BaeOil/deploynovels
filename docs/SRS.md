# Software Requirements Specification (SRS)

## ระบบแพลตฟอร์มเว็บแอปพลิเคชันสำหรับสร้างและอ่านนิยายทางเลือกแบบเลือกเส้นทาง

---

# 1. Introduction

## 1.1 Purpose

เอกสาร Software Requirements Specification (SRS) ฉบับนี้จัดทำขึ้นเพื่อระบุความต้องการของระบบแพลตฟอร์มเว็บแอปพลิเคชันสำหรับสร้างและอ่านนิยายทางเลือกแบบเลือกเส้นทาง โดยใช้เป็นเอกสารอ้างอิงร่วมกันในการออกแบบ พัฒนา ตรวจสอบ และทดสอบระบบ

กลุ่มผู้ใช้งานหลักของระบบประกอบด้วย ผู้เยี่ยมชม ผู้อ่าน นักเขียน และผู้ดูแลระบบ

---

## 1.2 Scope

ระบบมีวัตถุประสงค์เพื่อสนับสนุนการสร้างและอ่านนิยายแบบเลือกเส้นทาง โดยเนื้อเรื่องสามารถแตกแขนงออกเป็นหลายเส้นทางตามตัวเลือกที่ผู้อ่านเลือก

ขอบเขตของระบบประกอบด้วย

* การสมัครสมาชิกและเข้าสู่ระบบ
* การจัดการข้อมูลส่วนตัวของผู้ใช้งาน
* การค้นหาและเรียกดูนิยาย
* การจัดหมวดหมู่นิยาย
* การอ่านนิยายและเลือกเส้นทางของเนื้อเรื่อง
* การเพิ่มนิยายลงชั้นหนังสือ
* การติดตามนักเขียน
* การแจ้งเตือน
* การสมัครเป็นนักเขียนและการอนุมัตินักเขียน
* การสร้างและจัดการนิยาย
* การสร้างและจัดการตอน
* การสร้างและจัดการฉาก
* การสร้างและจัดการตัวเลือก
* การจัดการโครงสร้างเนื้อเรื่อง
* การกำหนดฉากเริ่มต้นและฉากจบ
* การแสดงตัวอย่างนิยายสำหรับนักเขียน
* การแสดงข้อมูลสถิติของนิยายสำหรับนักเขียน
* การจัดการหมวดหมู่โดยผู้ดูแลระบบ
* การจัดการบัญชีผู้ใช้งานโดยผู้ดูแลระบบ
* การจัดการคำขอสมัครนักเขียน
* การจัดการรายงานและคำขอที่เกี่ยวข้อง
* การตรวจสอบและจัดการนิยายที่เผยแพร่
* การบันทึกประวัติการดำเนินการของผู้ใช้งานในระบบ

ระบบมุ่งเน้นการสร้างและอ่านนิยายแบบเลือกเส้นทาง ไม่ได้มีวัตถุประสงค์เพื่อเป็นแพลตฟอร์มเกม

# 2. Overall Description

## 2.1 System Overview

ระบบเป็นแพลตฟอร์มเว็บสำหรับสร้างและอ่านนิยายทางเลือก โดยแบ่งการทำงานตามบทบาทของผู้ใช้งาน

### Guest

สามารถ

* เข้าสู่หน้าเว็บไซต์
* ค้นหานิยาย
* เรียกดูหมวดหมู่
* ดูรายละเอียดนิยาย
* อ่านนิยายที่เปิดเผยต่อผู้ใช้งานทั่วไป

### Reader

สามารถใช้ความสามารถของ Guest และสามารถ

* เข้าสู่ระบบ
* อ่านนิยายและเลือกเส้นทาง
* อ่านต่อจากตำแหน่งที่อ่านค้างไว้
* เพิ่มนิยายลงชั้นหนังสือ
* ติดตามนักเขียน
* รับการแจ้งเตือน
* จัดการข้อมูลส่วนตัว

### Writer

สามารถใช้ความสามารถของ Reader ได้ทั้งหมด และสามารถ

* สมัครเป็นนักเขียน
* สร้างและจัดการนิยายของตนเอง
* จัดการตอน
* จัดการฉาก
* จัดการตัวเลือก
* จัดการโครงสร้างเนื้อเรื่อง
* กำหนดฉากเริ่มต้น
* กำหนดฉากจบ
* ดูตัวอย่างนิยาย
* ดูข้อมูลสถิติของนิยาย

### Admin

สามารถ

* จัดการข้อมูลผู้ใช้งานตามสิทธิ์
* ตรวจสอบและอนุมัติคำขอสมัครนักเขียน
* จัดการหมวดหมู่
* ตรวจสอบนิยายที่เผยแพร่
* ระงับการเผยแพร่นิยายตามเงื่อนไขของระบบ
* จัดการรายงาน
* จัดการคำขอที่เกี่ยวข้องกับการปลดการระงับ
* ตรวจสอบประวัติการดำเนินการในระบบ

ระบบไม่มีบทบาท Super Admin

---

## 2.2 User Groups and Characteristics

### 2.2.1 ผู้เยี่ยมชม (Guest)

เป็นผู้ใช้งานที่ยังไม่ได้เข้าสู่ระบบ มีความสามารถในการค้นหา เรียกดู และอ่านนิยายที่ระบบเปิดให้ผู้ใช้งานทั่วไปเข้าถึง

### 2.2.2 ผู้อ่าน (Reader)

เป็นผู้ใช้งานที่เข้าสู่ระบบและต้องการอ่านนิยาย สามารถเพิ่มนิยายลงชั้นหนังสือและติดตามนักเขียนได้

การแจ้งเตือนแบ่งตามความสัมพันธ์ดังนี้

* นิยายที่เพิ่มลงชั้นหนังสือ → รับการแจ้งเตือนที่เกี่ยวข้องกับนิยายดังกล่าว
* นักเขียนที่ติดตาม → รับการแจ้งเตือนที่เกี่ยวข้องกับนักเขียนดังกล่าว

ระบบไม่มีฟังก์ชันติดตามนิยายโดยตรง

### 2.2.3 นักเขียน (Writer)

เป็นผู้ใช้งานที่ได้รับการอนุมัติให้เป็นนักเขียน

นักเขียนสามารถใช้ความสามารถของ Reader ได้ทั้งหมด และมีความสามารถเพิ่มเติมในการสร้างและจัดการนิยายของตนเอง

### 2.2.4 ผู้ดูแลระบบ (Admin)

เป็นผู้ใช้งานที่ได้รับสิทธิ์ในการดูแลระบบ สามารถจัดการข้อมูลและตรวจสอบการดำเนินงานของระบบตามสิทธิ์ที่กำหนด

---

## 2.3 Operating Environment

ระบบทำงานผ่านเว็บเบราว์เซอร์บนอุปกรณ์ที่สามารถเชื่อมต่ออินเทอร์เน็ตได้

ส่วนประกอบหลักของระบบประกอบด้วย

* Web Frontend
* Backend Server
* Database
* File/Object Storage
* Authentication และระบบตรวจสอบ Token

---

## 2.4 Constraints

* ผู้ใช้งานต้องได้รับการตรวจสอบสิทธิ์ก่อนเข้าถึงฟังก์ชันที่จำกัดตามบทบาท
* การดำเนินการที่เกี่ยวข้องกับสิทธิ์ของผู้ใช้งานต้องเป็นไปตามบทบาทที่ระบบกำหนด
* นักเขียนสามารถจัดการเฉพาะนิยายและข้อมูลที่ตนเองมีสิทธิ์จัดการ
* การดำเนินการของผู้ดูแลระบบต้องเป็นไปตามสิทธิ์ของ Admin
* นิยายที่แสดงต่อผู้ใช้งานทั่วไปต้องเป็นนิยายที่นักเขียนเลือกเผยแพร่
* โครงสร้างเนื้อเรื่องต้องไม่ทำให้เส้นทางของฉากเกิดวงจร
* การแก้ไขข้อมูลต้องไม่ทำให้ข้อมูลที่เกี่ยวข้องกับโครงสร้างนิยายเกิดความไม่สอดคล้องกัน

---

## 2.5 Assumptions and Dependencies

* ระบบมีฐานข้อมูลสำหรับจัดเก็บข้อมูลผู้ใช้งาน นิยาย ตอน ฉาก ตัวเลือก และข้อมูลที่เกี่ยวข้อง
* ระบบมีพื้นที่จัดเก็บไฟล์สำหรับข้อมูลที่จำเป็น
* ระบบมีระบบตรวจสอบสิทธิ์ของผู้ใช้งาน
* ผู้ใช้งานมีอุปกรณ์และเว็บเบราว์เซอร์ที่สามารถเข้าถึงระบบได้
* รายละเอียดของสถิติและความสามารถบางส่วนยึดตามความสามารถที่มีอยู่ในระบบปัจจุบัน

# 3. Specific Requirements

## 3.1 Functional Requirements

### 3.1.1 การสมัครสมาชิกและเข้าสู่ระบบ

**FR-AUTH-01** ระบบต้องให้ผู้ใช้งานสมัครสมาชิกด้วยข้อมูลที่ระบบกำหนด

**FR-AUTH-02** ระบบต้องตรวจสอบข้อมูลสำหรับเข้าสู่ระบบก่อนอนุญาตให้ผู้ใช้งานเข้าสู่ระบบ

**FR-AUTH-03** ระบบต้องสร้างข้อมูลสำหรับยืนยันตัวตนของผู้ใช้งานหลังจากเข้าสู่ระบบสำเร็จ

**FR-AUTH-04** ระบบต้องตรวจสอบสิทธิ์ของผู้ใช้งานก่อนเข้าถึงฟังก์ชันที่จำกัดตามบทบาท

**FR-AUTH-05** ระบบต้องให้ผู้ใช้งานออกจากระบบได้

---

### 3.1.2 การจัดการบัญชีผู้ใช้งาน

**FR-USER-01** ระบบต้องให้ผู้ใช้งานดูข้อมูลส่วนตัวของตนเองได้

**FR-USER-02** ระบบต้องให้ผู้ใช้งานแก้ไขข้อมูลส่วนตัวที่ระบบอนุญาตได้

**FR-USER-03** ระบบต้องให้ผู้ใช้งานจัดการข้อมูลบัญชีของตนเองได้ตามความสามารถที่มีอยู่ในระบบ

**FR-USER-04** ระบบต้องตรวจสอบสิทธิ์ก่อนดำเนินการกับข้อมูลบัญชีของผู้ใช้งาน

---

### 3.1.3 การค้นหาและอ่านนิยาย

**FR-READ-01** ระบบต้องให้ผู้ใช้งานค้นหานิยายได้

**FR-READ-02** ระบบต้องให้ผู้ใช้งานเรียกดูนิยายตามหมวดหมู่ได้

**FR-READ-03** ระบบต้องแสดงรายละเอียดของนิยายก่อนเริ่มอ่านได้

**FR-READ-04** ระบบต้องให้ผู้ใช้งานอ่านเนื้อหาของนิยายได้

**FR-READ-05** ระบบต้องแสดงตัวเลือกที่มีอยู่ในฉากให้ผู้ใช้งานเลือกได้

**FR-READ-06** ระบบต้องนำผู้ใช้งานไปยังฉากที่สัมพันธ์กับตัวเลือกที่เลือก

**FR-READ-07** ระบบต้องสามารถให้ผู้ใช้งานอ่านนิยายต่อจากตำแหน่งที่อ่านค้างไว้ได้

**FR-READ-08** ระบบต้องไม่แสดงนิยายหรือเนื้อหาที่นักเขียนยังไม่ได้เลือกเผยแพร่แก่ผู้ใช้งานทั่วไป

**FR-READ-09** ระบบต้องแสดงเฉพาะเส้นทางหรือข้อมูลของโครงสร้างเนื้อเรื่องที่ผู้ใช้งานสามารถเข้าถึงได้ตามสถานะการอ่าน

---

### 3.1.4 การอ่านและสถานะการอ่าน

**FR-PROG-01** ระบบต้องบันทึกตำแหน่งการอ่านของผู้ใช้งานตามความสามารถที่มีอยู่ในระบบ

**FR-PROG-02** ระบบต้องให้ผู้ใช้งานเลือกอ่านจากตำแหน่งที่ระบบบันทึกไว้ได้

**FR-PROG-03** การอ่านจากตัวอย่างหรือ Preview ของนักเขียนต้องไม่เปลี่ยนสถานะการอ่านของผู้ใช้งานทั่วไป

**FR-PROG-04** ระบบต้องให้ผู้ใช้งานเลือกอ่านจากตำแหน่งที่ต้องการได้ตามความสามารถของระบบ

---

### 3.1.5 ชั้นหนังสือ การติดตามนักเขียน และการแจ้งเตือน

**FR-FOLLOW-01** ระบบต้องให้ผู้ใช้งานเพิ่มนิยายลงชั้นหนังสือได้

**FR-FOLLOW-02** ระบบต้องให้ผู้ใช้งานนำนิยายออกจากชั้นหนังสือได้

**FR-FOLLOW-03** ระบบต้องให้ผู้ใช้งานติดตามนักเขียนได้

**FR-FOLLOW-04** ระบบต้องให้ผู้ใช้งานยกเลิกการติดตามนักเขียนได้

หมายเหตุ: ในกลุ่ม `FR-FOLLOW` นี้ `FR-FOLLOW-01` และ `FR-FOLLOW-02` เกี่ยวข้องกับชั้นหนังสือ (Bookshelf) ตาม Spec `007-bookshelf` ส่วน `FR-FOLLOW-03` และ `FR-FOLLOW-04` เกี่ยวข้องกับการติดตามนักเขียน ตาม Spec `008-follow-writer`

**FR-NOTI-01** ระบบต้องแสดงการแจ้งเตือนให้ผู้ใช้งานที่เกี่ยวข้องทราบตามเหตุการณ์ที่ระบบกำหนด

**FR-NOTI-02** ระบบต้องแสดงรายการแจ้งเตือนให้ผู้ใช้งานตรวจสอบได้

**FR-NOTI-04** เมื่อมีเหตุการณ์ที่เกี่ยวข้องกับนักเขียนที่ผู้ใช้งานติดตาม ระบบต้องแจ้งเตือนผู้ใช้งาน

**FR-STRUCT-05** ระบบต้องตรวจสอบความถูกต้องของโครงสร้างเนื้อเรื่องก่อนเผยแพร่ตามเงื่อนไขที่ระบบกำหนด

**FR-STRUCT-09** เมื่อมีการลบตอนที่ 1 ตอนที่ 2 ต้องเลื่อนขึ้นมาเป็นตอนที่ 1 และฉากแรกของตอนที่เลื่อนขึ้นมาต้องถูกกำหนดเป็นฉากเริ่มต้นโดยอัตโนมัติ

### 3.1.17 กฎตรวจสอบข้อมูล (Validation Rules)

**FR-VALID-01** ระบบต้องตรวจสอบข้อมูลขาเข้าตามกฎตรวจสอบที่กำหนดไว้ในตารางด้านล่าง โดยกฎชุดนี้เป็นแหล่งข้อมูลอ้างอิงเดียวกัน (single source of truth) ของเอกสาร Backend (`docs/SRS.md`, `docs/openapi.yaml`, `docs/specs/*`) และ Frontend และถูกบังคับใช้ที่ชั้น Backend

กฎตรวจสอบที่ถูกล็อกไว้ (Locked Validation Rules):

| Rule ID | ข้อกำหนด | ฟิลด์ / จุดที่ใช้ | ค่าที่ล็อก |
| ------- | --------- | ----------------- | ---------- |
| `VAL-01` | ชื่อเรื่องนิยาย | `title` (สร้าง/แก้ไขนิยาย) | ไม่เกิน 100 อักขระ |
| `VAL-02` | คำโปรยนิยาย (Tagline) | `captions` (Frontend ใช้ชื่อฟิลด์ `tagline`) | ไม่เกิน 200 อักขระ |
| `VAL-03` | ชื่อผู้ใช้ | `username` (สมัครสมาชิก / เปลี่ยนชื่อผู้ใช้) | 3-50 อักขระ |
| `VAL-04` | ข้อความตัวเลือก | `label` (สร้าง/แก้ไขตัวเลือก) | ไม่เกิน 80 อักขระ |
| `VAL-05` | ~~คำใบ้ของตัวเลือก~~ (ยกเลิก) | `hint` (ยกเลิกโดยการตัดสินใจของเจ้าของโครงการ — ระบบไม่จำเป็นต้องมีฟิลด์ `hint` และฐานข้อมูลปัจจุบันไม่มีคอลัมน์นี้) | ไม่นำไปใช้ |
| `VAL-06` | จำนวนหมวดหมู่ต่อนิยายหนึ่งเรื่อง | `category_ids` (สร้าง/แก้ไขนิยาย) | ไม่เกิน 3 หมวดหมู่ |
| `VAL-07` | ความสนใจของนักเขียนตอนยื่นคำขอสมัคร | `category_ids` / `genres` (ยื่นคำขอสมัครนักเขียน) | 3-5 รายการ |
| `VAL-08` | รูปปกนิยาย | `/upload/image` | ไม่เกิน 10MB |
| `VAL-09` | รูปโปรไฟล์ | `profileImage` / `avatar` | ไม่เกิน 5MB |
| `VAL-10` | ประเภทไฟล์ภาพที่รองรับ | การอัปโหลดรูปภาพทุกจุด | JPEG, PNG, WebP เท่านั้น |
| `VAL-11` | เนื้อหานิยาย/ฉากแบบยาว | `introduction` (นิยาย), `content` (ฉาก) | ไม่จำกัดจำนวนอักขระ |

หมายเหตุ:

* กฎ `VAL-01` ถึง `VAL-11` เป็นค่าที่ล็อกไว้แล้ว ห้ามแก้ไขในเอกสารหรือโค้ดโดยไม่ผ่านกระบวนการเปลี่ยนแปลง Requirement
* กฎที่ยังไม่ถูกบังคับใช้ใน Backend ปัจจุบันถือเป็นช่องว่างระหว่างเอกสารกับโค้ด และต้องได้รับการรายงานเป็น explicit conflict แทนการแก้ค่าในเอกสาร
* `VAL-05` (คำใบ้ของตัวเลือก `hint`) ถูกยกเลิกโดยการตัดสินใจของเจ้าของโครงการ เนื่องว่าระบบไม่จำเป็นต้องมีฟิลด์ `hint` และฐานข้อมูลปัจจุบันไม่มีคอลัมน์นี้ จึงไม่มีการบังคับใช้กฎนี้ และห้ามเพิ่มฟิลด์ `hint` ใน model, DTO, API contract หรือ validation
* เนื้อหานิยายและเนื้อหาฉากแบบยาว (`VAL-11`) ต้องไม่ถูกจำกัดจำนวนอักขระในชั้น Backend หรือ Frontend

# 3.2 External Interfaces

## 3.2.1 User Interface

ระบบต้องมีส่วนติดต่อผู้ใช้งานสำหรับ

* Guest
* Reader
* Writer
* Admin

โดยส่วนติดต่อผู้ใช้งานต้องแสดงฟังก์ชันตามสิทธิ์ของแต่ละบทบาท

---

## 3.2.2 Software Interface

ระบบต้องสามารถทำงานร่วมกับส่วนประกอบซอฟต์แวร์ที่จำเป็นต่อการจัดเก็บข้อมูล การจัดเก็บไฟล์ และการตรวจสอบสิทธิ์ของผู้ใช้งานตามสถาปัตยกรรมของระบบ

---

## 3.2.3 Communication Interface

ระบบต้องสามารถรับส่งข้อมูลระหว่างส่วนติดต่อผู้ใช้งานกับระบบประมวลผลผ่านเครือข่ายตามรูปแบบการสื่อสารที่ระบบกำหนด

# 3.3 Non-Functional Requirements

ในปัจจุบันยังไม่มีการกำหนดค่าเชิงตัวเลขสำหรับ Non-Functional Requirements เช่น Response Time, จำนวนผู้ใช้งานพร้อมกัน หรือปริมาณข้อมูลสูงสุดอย่างชัดเจน

ดังนั้นจึงไม่กำหนดตัวเลขขึ้นมาเองใน SRS ฉบับนี้ และจะพิจารณาเพิ่มเติมเมื่อมีข้อมูลหรือข้อกำหนดจากระบบที่ชัดเจน

# 3.4 Domain Requirements

## 3.4.1 การจัดการสิทธิ์

ระบบต้องจำกัดการเข้าถึงฟังก์ชันตามบทบาทของผู้ใช้งาน

## 3.4.2 การเผยแพร่นิยาย

นักเขียนเป็นผู้เลือกเผยแพร่นิยายของตนเอง และนิยายที่ยังไม่ได้เลือกเผยแพร่ต้องไม่แสดงต่อผู้ใช้งานทั่วไป

## 3.4.3 ความสัมพันธ์ของเนื้อเรื่อง

นิยายประกอบด้วยตอน ตอนประกอบด้วยฉาก และฉากสามารถมีตัวเลือกที่เชื่อมโยงไปยังฉากอื่น

โครงสร้างเนื้อเรื่องต้องไม่ทำให้เกิดวงจรของเส้นทาง

## 3.4.4 การจัดการเนื้อหาที่ถูกรายงาน

เมื่อรายงานได้รับการอนุมัติตามกระบวนการของระบบ นิยายที่เกี่ยวข้องต้องถูกระงับการเผยแพร่ตามเงื่อนไขของระบบ

## 4.5 Spec Versioning and Review Policy

นโยบายนี้กำหนดแนวทางสำหรับการเปลี่ยนแปลง Spec ทั้งหมดใน `docs/specs/` รวมถึงการบันทึก Version และ Last reviewed เพื่อให้เอกสารตรวจสอบย้อนกลับได้และสะท้อนประวัติการแก้ไขจริง

### 4.5.1 Versioning

* การแก้คำสะกด รูปแบบ หรือการจัดหน้า โดยไม่เปลี่ยนความหมายของข้อกำหนด: ไม่จำเป็นต้อง bump Version
* การแก้ Requirement, Rule, Constraint หรือ Acceptance Criteria ที่มีผลต่อความหมายของ Spec: ให้พิจารณา bump minor version (เช่น `1.0 → 1.1`)
* การเพิ่มหรือแก้ Requirement/Acceptance Criteria ที่ได้รับการยืนยันจากเจ้าของโครงการ: ให้พิจารณา bump minor version
* การปิด Open Question ที่ทำให้ข้อกำหนดหรือการตัดสินใจของ Spec เปลี่ยนแปลงไป: ให้พิจารณา bump minor version
* การปิด Open Question ที่เพียงบันทึกข้อยุติของข้อกำหนดเดิม โดยไม่เปลี่ยนแปลงความหมายของ Spec: ให้พิจารณาตามผลกระทบจริง และไม่ bump โดยอัตโนมัติ
* ห้ามเพิ่มเลข Version หากไม่มีการเปลี่ยนแปลงเนื้อหาที่รองรับการ bump

### 4.5.2 Last reviewed

* อัปเดต `Last reviewed` เฉพาะเมื่อมีหลักฐานว่ามีการตรวจสอบ (review) ข้อกำหนดอย่างเป็นทางการ
* การแก้ไขไฟล์ การปิด Open Question การ commit หรือการดูจาก modified time ไม่ถือเป็นหลักฐาน Formal Review โดยอัตโนมัติ
* หากไม่มีหลักฐานการตรวจสอบอย่างเป็นทางการ ให้คงค่า `ยังไม่ได้ Review` ไว้
* การตรวจสอบอย่างเป็นทางการโดยที่ไม่เปลี่ยนแปลงเนื้อหา สามารถอัปเดต `Last reviewed` ได้โดยไม่ต้อง bump Version
* วันที่ใน `Last reviewed` ต้องอ้างอิงจากหลักฐานที่ตรวจสอบได้ ห้ามอนุมานจากวันที่ปัจจุบันหรือจากวันที่แก้ไขไฟล์

### 4.5.3 ขอบเขตการใช้นโยบาย

* นโยบายนี้ใช้เป็นแนวทางสำหรับการเปลี่ยนแปลง Specs ตั้งแต่นี้เป็นต้นไป
* ห้ามใช้การเพิ่มนโยบายนี้เป็นเหตุผลในการ bump Version หรือเปลี่ยน `Last reviewed` ของ Specs ทั้งหมดโดยอัตโนมัติ
* การตัดสินใจเรื่อง Version และ `Last reviewed` ของแต่ละ Spec ต้องพิจารณาจากการเปลี่ยนแปลงเนื้อหาจริงและหลักฐานการตรวจสอบของ Spec นั้น ๆ
